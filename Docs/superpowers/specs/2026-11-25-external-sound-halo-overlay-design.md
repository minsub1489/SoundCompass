# 게임 밖 Sound Halo 오버레이 설계

작성일 2026-11-25. 대상 저장소 `minsub1489/SoundCompass`, 작업 브랜치 `PSH`.

## 1. 의도

언리얼 안에 있는 Sound Halo(`USoundHaloWidget`)를 게임 밖으로 옮겨, 어떤 PC 게임 위에든 띄울 수 있는 오버레이로 만듭니다. 게임 안에서는 소리의 종류, 방향, 거리를 엔진이 알려 주지만, 게임 밖에서는 시스템 출력 오디오만 들을 수 있습니다. 그래서 출력 오디오를 분석하는 모델(현재 `Saved/ModelEval`에서 평가 중)이 엔진을 대신합니다.

게임 안 Halo의 표시 규칙은 그대로 지킵니다. 화면 중앙은 비워 두고, 아이콘은 처음 들릴 때만 잠깐 진하고 곧 10% 불투명도로 가라앉으며, 기본 화면에는 글자를 쓰지 않습니다. 색은 소리의 종류, 크기와 링 두께는 위험도를 뜻합니다.

## 2. 목표, 비목표, 반목표

목표:

- 게임 프로세스를 건드리지 않고, 테두리 없는 창 모드로 실행한 게임 위에 Halo를 띄웁니다.
- 스테레오(단순 패닝 또는 바이노럴) 출력과 5.1/7.1 출력을 모두 받습니다. 7.1에서는 360° 방위를, 스테레오에서는 좌우 방위와 앞뒤 신뢰도를 보여 줍니다.
- 모델이 준비되기 전에도 언리얼 테스트 맵의 정답 데이터로 오버레이를 개발하고, 모델이 붙은 뒤에는 정답과 모델 출력을 비교할 수 있게 합니다.
- 모델을 설정으로 바꿀 수 있게 합니다. 분석기는 `Saved/ModelEval`의 어댑터 규약(`Adapter.predict(audio, sr)`)을 그대로 씁니다.

비목표:

- 독점 전체화면 지원과 DirectX 후킹(코드 주입).
- Windows Sonic, Dolby Atmos 같은 공간 음향 엔드포인트의 다채널 해석. 이 경우 루프백에는 이미 바이노럴로 렌더링된 스테레오가 잡히므로 스테레오 경로로 처리합니다.
- 7.1 경로에서 같은 시각에 겹친 여러 음원의 분리. 1차 구현은 클래스마다 가장 강한 방향 하나만 냅니다.
- 게임별 거리 보정 UI, 설정 UI, 설치 프로그램, macOS와 Linux.
- 모델 학습과 모델 선정. 선정은 `Saved/ModelEval`에서 따로 진행합니다.
- 언리얼 쪽 기하 코드와 오버레이 쪽 기하 코드의 통합.

반목표(기술적으로 동작해도 실패로 보는 것):

- 오버레이가 화면 중앙을 가리거나 상대를 가리는 경우.
- 기본 화면에 글자가 나오는 경우.
- 오버레이 때문에 게임 프레임이 눈에 띄게 떨어지거나, 오버레이가 포커스나 입력을 가져가는 경우.
- 게임 프로세스의 메모리나 렌더링 파이프라인에 접근하는 경우.

## 3. 제약

- 입력은 기본 출력 장치의 WASAPI 루프백뿐입니다. 채널 수는 장치 설정에 따라 2, 6(5.1), 8(7.1)입니다.
- 분석 모델은 모노 또는 바이노럴 스테레오 입력을 받습니다. 많은 게임이 스테레오를 HRTF 없이 단순 패닝으로 내보내므로, 이 경우 스테레오에는 앞뒤 정보가 없습니다. GCC-PHAT 기준선의 앞뒤 혼동률은 44%였습니다.
- 스테레오에서 고도는 거의 추정되지 않습니다. 거리는 게임마다 감쇠 곡선이 달라 보정 전에는 near(5m 미만), mid(5~15m), far(15m 이상) 세 구간 정도가 현실적입니다.
- 게임 밖에서는 캐릭터 위치와 카메라 피치를 모릅니다. 방위는 오디오 리스너 기준이고, 링을 보는 가상 카메라의 피치는 고정값입니다.
- 분석기와 오버레이는 게임과 같은 PC에서 CPU와 GPU를 나눠 씁니다. 목표 사용자 GPU는 GTX급입니다.
- 언리얼 C++ 클래스를 추가하거나 바꿀 때는 Live Coding을 쓰지 않습니다. 에디터를 저장하고 닫은 뒤 `Build.bat`으로 빌드합니다. 에디터를 닫기 전에는 사용자에게 매번 묻습니다.

## 4. 검토한 접근

| 접근 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 분석기 + 별도 오버레이 프로세스 (채택) | Python 분석기가 루프백을 분석해 localhost UDP로 이벤트를 보내고, C++ 오버레이가 투명 최상위 창에 그림 | 게임에 주입하지 않음, 모델 교체가 쉬움, 언리얼도 같은 메시지를 보내 정답 비교 가능 | 독점 전체화면 게임에서는 보이지 않음 |
| B. DirectX 후킹 오버레이 | 게임의 Present를 가로채 게임 화면에 직접 그림 | 독점 전체화면에서도 보임 | 안티치트에 걸릴 위험, 게임과 그래픽 API별 대응, 게임 충돌 위험 |
| C. 언리얼 패키지 앱을 투명 창으로 실행 | 지금 위젯 코드를 그대로 쓰는 독립 UE 앱 | 그리기 코드 재사용 | 투명 창 지원이 약하고, 게임 옆에서 돌리기에 무거움 |

A를 채택했습니다. 사용자가 스테레오와 7.1을 모두 지원하기로 정했습니다.

오버레이 구현 방식은 설계자 판단으로 정했습니다. C++(Win32, Direct3D 11, DirectComposition, Direct2D)를 씁니다. `SoundHaloGeometry.h`는 `FVector`와 `FMath`만 작은 수학 구조체로 바꾸면 그대로 옮겨지고, `SoundPresentation.h`와 `SoundImportancePolicy.h`는 표준 C++만 써서 수정 없이 쓸 수 있습니다. Qt나 Electron의 반투명 전체화면 창은 매 프레임 화면 전체를 CPU로 복사하는 경우가 많아 게임 옆에서 부담이 될 수 있다고 판단했습니다(측정하지 않은 추정입니다).

## 5. 구성

```
 [게임] ── 오디오 출력 ──> WASAPI 루프백
                              │
                     [분석기 analyzer, Python]
                      ├ 2ch  → 스테레오 경로
                      └ 6/8ch → 서라운드 경로
                              │ UDP 127.0.0.1:47800, JSON
 [UE 테스트 맵] ─ 정답 프레임 ─┤ (같은 형식, 개발용)
                              ▼
                     [오버레이 overlay, C++]
                      투명, 클릭 통과, 최상위 창
```

코드는 저장소 최상위의 새 폴더 `HaloOverlay/`에 둡니다(git으로 추적).

- `HaloOverlay/analyzer/`: Python 분석기.
- `HaloOverlay/overlay/`: C++ 오버레이(CMake, MSVC 2022).
- `HaloOverlay/tools/`: 메시지 기록 재생, 7.1 시험 신호 생성 같은 개발 도구.

## 6. 메시지 형식

분석기와 언리얼은 `127.0.0.1:47800`(설정으로 변경 가능)으로 UDP 데이터그램 하나에 JSON 하나를 보냅니다. 분석기는 분석 홉마다(약 10 Hz), 언리얼은 약 30 Hz로 보냅니다.

```json
{
  "v": 1,
  "src": "model",
  "mode": "stereo",
  "t": 1234.567,
  "events": [
    {
      "id": 17,
      "cls": "Gunshot",
      "conf": 0.82,
      "az": 35.0,
      "fb": 0.2,
      "dist_m": null,
      "dist_bin": "mid",
      "dist_src": "level",
      "elev_m": null,
      "level": 0.7
    }
  ]
}
```

- `src`: `"model"` 또는 `"ue"`. `mode`: `"stereo"`, `"surround"`, `"ground_truth"`. `t`: 보낸 쪽의 단조 시계(초).
- `events`: 그 순간 들리는 소리 목록입니다. 소리가 끝나면 목록에서 빠지고, 남은 표시와 서서히 사라지는 처리는 오버레이가 합니다.
- `id`: 보낸 쪽이 정하는 추적 번호입니다. 같은 소리가 이어지는 동안 유지됩니다.
- `cls`: 아래 15개 중 하나입니다. 모델 평가 클래스 14개(`Alarm, Dog, Door, Explosion, Fire, Footstep, GlassBreak, Gunshot, Impact, Item, Reload, Throwable, Vehicle, Voice`)에 `Other`를 더했습니다. `Other`는 언리얼 송신에서만 나옵니다.
- `conf`: 분류 확신도(0~1)입니다. 언리얼 송신은 1입니다.
- `az`: 도 단위 방위입니다. 0 정면, +90 오른쪽, ±180 뒤입니다.
- `fb`: 앞뒤 신뢰도(0~1)입니다. 1이면 `az`를 360° 그대로 믿습니다. 0이면 좌우 성분만 믿을 수 있다는 뜻이고, `az`는 앞쪽 반원(-90~90)으로 접은 값입니다.
- `dist_m`, `dist_bin`, `elev_m`: 모르면 `null`입니다. `dist_m`이 있으면 오버레이는 그 값을 쓰고, 없으면 `dist_bin`을 씁니다.
- `dist_src`: 거리의 출처입니다. `"model"`은 공간 어댑터, `"level"`은 크기 추정(7절), `"ue"`는 언리얼 정답입니다. 거리가 없으면 `null`입니다.
- `level`: 리스너에서의 크기를 dB로 잰 뒤 `(dB + 60) / 60`으로 0~1에 맞춘 값입니다(-60 dB 이하는 0, 0 dB 이상은 1). 오버레이는 이 값의 시간 기록으로 엔벨로프를 만듭니다.

## 7. 분석기

1. 기본 출력 장치를 WASAPI 루프백으로 엽니다. 장치 샘플레이트(보통 48 kHz)로 받고, 모델마다 필요한 샘플레이트로 바꿉니다. 출력 장치가 바뀌면 다시 엽니다.
2. 길이 1초 창을 100 ms마다 분석합니다.
3. 채널 수가 2이면 스테레오 경로, 6 또는 8이면 서라운드 경로를 씁니다.
4. 소리 있음 판정: 지금 어댑터는 이긴 클래스 하나만 돌려주고 "소리 없음"을 내지 않습니다. `evaluate.py`는 onset이 있는 구간만 넣으니 문제가 없지만, 실시간으로 홉마다 돌리면 배경 음악과 앰비언스 때문에 이벤트가 계속 나옵니다. 그래서 다음 두 가지를 둡니다.
   - 어댑터 결과 dict에 선택 키 `scores`(클래스 이름에서 0~1 확률로 가는 dict)를 추가합니다. `pick_class`가 이미 계산하는 클래스별 최대값을 그대로 담으면 됩니다. 키를 추가할 뿐이라 `evaluate.py`와 호환됩니다.
   - 분석기는 이벤트를 내기 전에 두 관문을 둡니다. 첫째, 대역 에너지가 최근 수 초의 배경 수준보다 일정 이상 올라간 onset이 있거나, 이미 추적 중인 이벤트가 이어지는 중이어야 합니다. 둘째, 해당 클래스의 `scores` 값이 클래스별 임계값 이상이어야 합니다. 두 관문을 통과한 클래스의 `scores` 값이 `conf`가 됩니다. 임계값은 `Saved/ModelEval` 장면으로 맞춥니다.
5. 스테레오 경로:
   - 분류는 설정된 분류 어댑터에 모노 다운믹스를 넣어 얻습니다.
   - 방향과 거리는 설정된 공간 어댑터에 스테레오를 넣어 얻습니다.
   - 클래스는 항상 분류 어댑터가 정합니다. 공간 어댑터가 여러 이벤트나 자기 클래스를 내면, 클래스가 같은 공간 이벤트의 방향을 쓰고, 같은 것이 없으면 가장 강한 공간 이벤트의 방향을 가장 확률이 높은 클래스에 붙입니다.
   - `fb`는 어댑터별 고정값으로 설정 파일에 둡니다. 기본값은 모든 스테레오 어댑터에서 0입니다. Spatial-AST처럼 360°를 내는 어댑터도 단순 패닝 게임에서는 뒤쪽 답이 추측이기 때문입니다. 게임 출력이 바이노럴인지 단순 패닝인지 자동으로 판별하는 기능은 이번 범위에 넣지 않습니다.
   - 모델 선정 전 기본값은 GCC-PHAT 기준선(`gcc_phat.py`)과 EfficientAT mn10입니다.
6. 서라운드 경로:
   - 분류는 모노 다운믹스로 스테레오 경로와 같게 합니다.
   - 방향은 모델 없이 구합니다. 주파수 대역마다 채널 에너지를 구하고, 스피커 방향 단위벡터를 에너지로 가중 합산해 방위를 냅니다. 채널 순서는 Windows 기본(FL, FR, FC, LFE, BL, BR, SL, SR)이고, 스피커 방위는 FC 0°, FL/FR ±30°, SL/SR ±90°, BL/BR ±150°로 둡니다. LFE는 뺍니다. 5.1은 BL/BR 없이 SL/SR을 ±110°로 둡니다.
   - 분류 결과와 방향은 에너지가 가장 큰 방향 봉우리를 가장 확률이 높은 클래스에 붙이는 방식으로 연결합니다(1차 구현).
   - `fb`는 1입니다.
7. 거리: 공간 어댑터가 거리를 내면 그 값을 씁니다. 내지 않으면(기본 구성과 서라운드 경로는 늘 이 경우입니다) 크기로 `dist_bin`을 추정합니다.
   - 게임은 같은 효과음 에셋을 반복해서 쓰므로, 클래스를 알면 크기가 거리 단서가 됩니다.
   - 클래스마다 기준 크기를 둡니다. 시작값은 클래스별 기본표이고, 실행 중에는 이번 세션에서 그 클래스로 들린 소리의 상위 크기(예: 최근 수 분의 95번째 백분위)로 갱신합니다. 세션 안의 상대값이라 Windows 볼륨이나 게임 마스터 볼륨이 달라도 결과가 크게 흔들리지 않습니다.
   - 이벤트의 onset 근처 최대 크기가 기준보다 얼마나 작은지(dB)로 구간을 정합니다. 시작값은 6 dB 이내면 near, 6~18 dB면 mid, 그보다 작으면 far입니다. 거리 두 배마다 약 6 dB 줄어드는 가정에서 나온 값이고, `Saved/ModelEval` 장면(거리 라벨 있음)으로 다시 맞춥니다.
   - 한 클래스의 소리가 세션에서 아직 3번 미만으로 들렸고 기본표에도 값이 없으면 `dist_bin`은 `null`입니다.
   - 추정값이라는 점을 메시지에 남기도록 `dist_src`(`"model"`, `"level"`, `"ue"`) 키를 보냅니다. 오버레이는 1차 구현에서 이 값으로 표시를 바꾸지 않습니다.
8. 직전 홉의 이벤트와 클래스가 같고 방위 차가 20° 이내이면 같은 `id`를 이어 씁니다.
9. 어댑터는 처음에는 설정된 경로(기본 `Saved/ModelEval/adapters`)에서 불러옵니다. 모델이 정해지면 그 어댑터만 `HaloOverlay/analyzer/`로 옮깁니다. 가중치는 지금 노트북에만 있으므로 실행할 PC로 복사해야 합니다.
10. 추론 장치는 CUDA가 있으면 GPU, 없으면 CPU입니다(설정 가능). EfficientAT은 1초 청크를 10초로 0 패딩해서 넣기 때문에, 홉마다 10초 입력을 추론하는 셈입니다. 측정해서 성능 목표를 넘으면 분류만 홉을 늘리거나(예: 250 ms) 패딩 길이를 줄여도 됩니다. 이때 정확도 변화는 `evaluate.py`로 확인합니다.
11. 파일 입력 모드를 둡니다. 루프백 대신 WAV 파일을 실시간 속도로 흘려, `Saved/ModelEval/data`의 장면으로 분석기를 시험합니다.

## 8. 오버레이

창:

- 설정한 모니터(기본 주 모니터) 전체를 덮는 창 하나를 만듭니다. 확장 스타일은 `WS_EX_TOPMOST | WS_EX_TRANSPARENT | WS_EX_LAYERED | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_NOREDIRECTIONBITMAP`입니다. 포커스와 입력을 가져가지 않습니다.
- 그리기는 DirectComposition에 연결한 사전곱 알파 스왑체인에 Direct2D로 합니다. 보이는 소리가 있을 때만 약 60 Hz로 다시 그리고, 없으면 그리기를 멈춥니다.

표시 로직(게임 안 Halo를 옮기고, 게임 밖 조건에 맞게 바꾼 부분):

- 중앙 링, 범위 링, 사면체 포인터, 가장자리 아이콘, 처음 들릴 때의 파동은 `SoundHaloWidget.cpp`의 `NativePaint`를 옮깁니다. 크기와 투명도 기본값은 `SoundHaloWidget.h`의 속성 기본값을 따릅니다.
- 가상 카메라 피치는 30°로 고정합니다(설정 가능).
- 범위 링은 5/15/30 m 링과 40 m 이상 점선 링을 그대로 그립니다. `dist_m`이 없으면 포인터를 `dist_bin` 구간의 가운데(near 2.5 m, mid 10 m, far 30 m)에 세웁니다. 아이콘 반경과 `Score`의 근접도 항도 같은 값을 씁니다.
- `dist_m`과 `dist_bin`이 모두 없으면 포인터를 그리지 않고, 중앙 링만 그 방위를 밝히며, 아이콘은 가까운 원과 가장자리 타원의 중간 반경에 둡니다.
- `elev_m`이 없으면 포인터를 수평으로 세웁니다.
- 앞뒤가 불확실한 소리(`fb` < 0.5)는 `az`와 그 앞뒤 거울상(180° - `az`) 두 곳에 그립니다. 두 표시는 각각 원래 불투명도의 절반이고, 중앙 링도 두 방위를 모두 밝힙니다.
- 반복되는 소리는 월드 좌표 대신 같은 `id`, 또는 같은 클래스이면서 방위 차가 20° 이내인 것으로 합칩니다.
- 차폐 표시(회색)는 정보가 없으므로 그리지 않습니다.
- 유지와 서서히 사라지는 처리는 `SoundPresentation.h`의 `Retention`과 `EnvelopeTrail`을, 표시 우선순위는 `SoundImportancePolicy.h`의 `Score`를 씁니다. 두 헤더는 `Source/SoundCompass/SoundVisualization/`을 include 경로에 넣어 복사 없이 씁니다. 클래스별 기본 중요도 표는 오버레이에 둡니다.
- 한 화면에 아이콘은 중요도 순으로 최대 4개입니다(`MaxEdgeMarkers`).

색과 아이콘:

- 기존 클래스는 지금 색을 그대로 씁니다. 언리얼의 Conversation은 Voice, Alert는 Alarm, Throw는 Throwable 색을 이어받습니다.
- 새 클래스(Dog, Fire, Impact, Item, Reload, Vehicle, Other)의 색은 구현자가 정합니다. 서로 구분되는 색상이어야 하고, 빨강 계열은 Gunshot에만 씁니다.
- 아이콘은 `Content/Ariel_NewMaterial/Ariel_*` 텍스처를 에디터에서 PNG로 한 번 내보내 `HaloOverlay/overlay/icons/`에 두고 WIC로 읽습니다. 아이콘이 없는 클래스는 지금처럼 파동 모양을 직접 그립니다.

조작:

- 전역 단축키 Ctrl+Alt+L로 이름과 거리 표시를 켜고 끕니다(게임 안의 F1에 해당). F1은 게임과 겹치는 경우가 많아 쓰지 않습니다.
- 전역 단축키 Ctrl+Alt+Q로 종료합니다.
- 설정 파일은 실행 파일 옆의 JSON 하나입니다. 포트, 모니터, 단축키, 카메라 피치, 받을 `src` 필터만 둡니다.

## 9. 언리얼 쪽 변경

- `USoundVisualizationSubsystem`에 UDP 송신을 추가합니다. 콘솔 변수 `SoundCompass.ExternalOverlay`(기본 0)를 켜면 매 틱이 아니라 약 30 Hz로 보냅니다.
- 보내는 값은 리스너 기준 프레임 값 그대로입니다(`AzimuthDegrees`, `DistanceMeters`, `ElevationMeters`). 게임 안 Halo처럼 캐릭터 기준으로 다시 재지 않습니다. 모델이 듣는 기준과 맞추기 위해서입니다.
- 카테고리는 6절의 클래스 이름으로 바꿔 보냅니다. Conversation은 Voice, Alert는 Alarm, Throw는 Throwable로 보내고, 대응이 없는 Ambience와 Noise는 Other로 보냅니다. 단, Noise의 하위 이름에 heli, plane, aircraft, engine, car, traffic이 들어 있으면 Vehicle로 보냅니다.
- `fb`는 1, `level`은 `Clamp((EstimatedListenerDb + 60) / 60, 0, 1)`, `id`는 `SourceId`입니다. 들리는 동안(`bPlaying`)인 프레임만 보냅니다.
- 이 기능은 개발과 비교용이라 출시 빌드에서는 꺼 둡니다.

## 10. 검증

- 서라운드 방위: 알려진 스피커 방향으로 패닝한 7.1 시험 신호를 만들어 분석기에 넣고, 방위 오차가 10° 이내인지 확인하는 자체 시험을 둡니다. 또 `gen_scenes.py`에 간단한 7.1 패너를 추가해 같은 장면을 7.1로도 만들고, `evaluate.py`로 서라운드 경로를 평가합니다.
- 스테레오 경로: 파일 입력 모드로 `Saved/ModelEval/data` 장면을 흘리고, 나온 이벤트를 `labels.csv`와 비교합니다.
- 오버레이: 언리얼이 보낸 메시지를 기록해 두고 재생 도구로 다시 보내 화면을 확인합니다. 화면 확인은 사용자가 직접 합니다.
- 정답과 모델 비교: 오버레이는 한 번에 한 `src`만 그립니다(설정의 `src` 필터). 두 스트림을 한 화면에 겹쳐 그리는 두 번째 표시 방식은 만들지 않습니다. 대신 `HaloOverlay/tools/`에 비교 도구를 둡니다. 이 도구는 같은 포트를 듣고(오버레이와 포트를 나눠 쓰도록 `SO_REUSEADDR`, 또는 분석기와 언리얼이 비교 도구 포트로도 보내는 설정) 두 스트림을 기록합니다. 그리고 언리얼 이벤트마다 1초 안에 처음 나온, 클래스가 같고 방위 차가 30° 이내인 모델 이벤트를 짝지어 클래스 정확도, 방위 오차, 앞뒤 혼동, 놓친 소리를 셉니다.
- 성능: 게임 하나에서 오버레이와 분석기(실제 모델 포함)를 켰을 때와 껐을 때의 프레임을 비교합니다. 목표는 오버레이 그리기 GPU 시간 프레임당 1 ms 이하, 분석기와 오버레이를 합친 CPU 사용률 5% 이하, 게임 평균 프레임 하락 5% 이하입니다(설계자 판단 목표치). 분석기가 GPU를 쓰면 추론 시간과 VRAM도 기록합니다.
- 지연: 소리가 난 뒤 오버레이에 나타날 때까지 200 ms 이하를 목표로 합니다. 비교 도구에서 짝지은 두 이벤트의 수신 시각 차이(모델 이벤트 수신 시각에서 언리얼 이벤트 수신 시각을 뺀 값)로 잽니다. 두 시각은 같은 PC의 같은 시계로 찍으므로 보낸 쪽 `t`의 시계가 달라도 됩니다. 여기에 오버레이의 그리기 지연(수신에서 화면 표시까지, 한 프레임 이하로 예상)을 더합니다.

## 12. 설계자 판단으로 정한 것

다음은 사용자와 논의하지 않고 설계자가 정했습니다. 검토가 필요합니다.

- 오버레이를 C++(Direct2D, DirectComposition)로 만드는 것.
- UDP 포트 47800, 분석 창 1초와 홉 100 ms.
- 단축키 Ctrl+Alt+L, Ctrl+Alt+Q.
- 앞뒤가 불확실하면 두 곳에 절반 불투명도로 그리는 표시 방식.
- 크기로 거리 추정하는 방식의 세부(세션 기준 크기, 6/18 dB 경계, 3번 미만이면 `null`). 크기로 추정한다는 결정 자체는 사용자가 정했습니다.
- 거리 구간별 포인터 위치(2.5/10/30 m).
- 성능과 지연 목표치.
- 코드 위치 `HaloOverlay/`.
- 소리 있음 판정(onset 관문과 클래스별 임계값)과 어댑터 결과의 선택 키 `scores`.
- 클래스는 분류 어댑터가 정하고, 공간 어댑터의 `fb`는 설정 파일의 어댑터별 고정값(기본 0)으로 두는 것.
- 정답과 모델 비교를 화면 겹치기 대신 기록과 짝짓기 도구로 하는 것, 지연을 그 도구로 재는 것.
- 추론 장치 기본값(CUDA 우선)과 성능 목표를 넘을 때 분류 홉을 늘리는 것.
